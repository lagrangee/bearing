# Bearing Project Orientation

Load this shared protocol only after an explicit request for Active-project Bearing Project Orientation or an accepted Fresh offer. It is never ambient, timer-driven, Portal-triggered, or implied by ordinary Bearing activation. An explicit Active-project request enters this protocol directly without entering Setup or replaying Fresh onboarding.

## Evidence Acquisition

Begin only after the user's request or acceptance. Consume the current Project Summary and complete Project Sitemap when available, then read relevant canonical planning, primary project documentation, manifests, and the top-level source and test topology. Deepen the read only where an unresolved question or candidate direction requires current source evidence. Do not crawl the repository, build an index, or exhaustively read history.

Use the Bearing Scope Review acquisition boundary from `governance-disposition` for one transient Work Management inventory. First obtain project-level scope and lifecycle summaries, including open, blocked, and resolved counts. Expand active or open work, then only the completed work required to establish the current delivered baseline. Do not expand all historical tickets by default. Discard the inventory before completing the protocol; never persist it or expand Bearing Scope.

Preserve evidence classes in notes and output:

- repository facts come from current project files;
- native-work facts come from current provider evidence;
- canonical planning facts come from current Bearing sources;
- agent inferences remain labelled as inferences;
- unavailable, stale, partial, or conflicting evidence retains that state; and
- unresolved questions remain questions rather than inferred facts.

Relevant completed tickets are evidence only for the completed baseline and future candidates. Never reconstruct a historical Roadmap, Gate, Gate Passage, Passage Evidence, Source Event Time, or other retroactive lifecycle from current work or repository history.

## Orientation Output

Return one current, reviewable orientation in the user's language with:

1. current project understanding and boundaries;
2. the completed baseline supported by evidence;
3. the active, open, and blocked work landscape;
4. a Project Summary draft;
5. zero or more future Roadmap horizons, each with ordered candidate Gates;
6. supporting evidence with repository facts, native-work facts, and canonical facts kept distinct;
7. labelled agent inferences; and
8. unresolved questions and evidence limitations.

Always include an explicitly labelled Project Summary draft, including for a `partial` outcome with evidence limitations. Zero Roadmap candidates is a valid outcome when evidence does not support a useful future horizon; state that result explicitly and never omit the Project Summary draft. Project Orientation defaults to project direction, not Efforts or Work Bindings, and does not design delivery scope unless a later explicit request enters the owning capability.

## Mutation Boundary

Project Orientation is read-only. It creates no Project Brief and writes no Project Summary, Roadmap, Gate, Effort, Work Binding, provider-native work, Portal state, Project Snapshot, inventory, cache, selection, receipt, or offered marker. Reading standalone work never enrolls it.

The user may approve, reject, refine, or defer any draft or candidate in ordinary conversation. Only explicit acceptance may continue to mutation. Route an accepted Summary draft to the Summary owner, an accepted Roadmap change to the Roadmap owner, and accepted Gate changes to the Gate owner in dependency-safe order. Each owner performs its own inspection, proposal, acceptance, write, and validation contract; Orientation supplies context but no mutation authority.

Bearing Scope Review remains the narrow transient inventory and enrollment-review boundary used as one input. It is not a substitute for Project Orientation, and Orientation does not broaden its discovery or persistence permissions. Discard every transient inventory and recommendation at completion and never expand Bearing Scope from the read.

## Outcome

Return `applied` when the read-only orientation is complete, `partial` when bounded evidence limitations remain visible but a useful orientation is possible, or `blocked` when trustworthy project evidence cannot support the requested orientation. These outcomes describe the conversation result only; they never become lifecycle, readiness, completion, or passage facts.

## Completion Criterion

The output separates repository facts, native-work facts, canonical planning facts, agent inferences, and unresolved questions; every transient inventory is discarded; no canonical, native, Portal, or repository mutation occurred; and any follow-up proposal still awaits explicit acceptance and its owning capability.
