# Feature Intake

## Applicability

Use when a feature request has an explicit or high-confidence material relationship to accepted
Roadmap, Gate, Effort, Work Binding, or cross-scope coordination commitments, or exposes a
high-confidence material opportunity for a new Roadmap horizon, Gate boundary, or Effort
commitment. An ordinary feature request continues through normal native delivery without this
journey. Do not use for ordinary maintenance, an exact known Ticket, or a direct executor
invocation whose scope is already accepted.

## Authority

The Human owns the disposition of only a related native scope and acceptance of every planning
candidate offered through this journey. The Agent owns one minimal read-only orientation, scope
boundaries, relationship judgment, and evidence-backed recommendations. Work Management and
Execution remain usable for unrelated or Human-selected Standalone Native Work; Bearing owners
govern only Human-accepted Bearing Scope.

## Operation

1. Perform one minimal read-only orientation from current Project Context, relevant planning facts,
   the requested outcome, and the smallest native-work view needed to identify scope boundaries.
   Completion: current relevance, existing coverage, and evidence limits are explicit without a
   full Project Orientation or repository-wide provider traversal.
2. Identify each proposed native scope by separable delivery outcome, not by an arbitrary Ticket or
   file count. Give one evidence-backed recommendation only for a scope with the required material
   relationship or planning opportunity. Continue every unrelated scope without either condition
   through ordinary native delivery. Completion: each recommendation and each ordinary delivery
   boundary is distinct.
3. When that high-confidence relationship exists, ask once before implementation whether the Human
   wants to place only the related native scope in Bearing Scope through an Effort and Work Binding,
   or keep it as Standalone Native Work. One answer may cover several clearly related visible scopes
   and may also accept a complete planning candidate shown with that choice. When no complete
   candidate is visible, the answer selects only the disposition. Completion: every scope that
   requires disposition has an explicit Human choice and no fixed confirmation count. A request
   that directly names an accepted Roadmap or Gate has an explicit relationship, but that
   relationship alone creates no Effort, Work Binding, or implementation authority. A limit from
   another planning operation, such as a request not to create an Effort while defining a Roadmap
   or Gate, is not a disposition for a later native scope. Never reuse it as a Standalone Native
   Work choice.
4. When the feature exposes a material planning opportunity without an accepted commitment, select
   only the semantic owner whose meaning would change: Roadmap for an outcome horizon, Gate for a
   decision boundary, or Effort for a delivery commitment. Offer one proportionate recommendation
   when that decision is useful. The timing remains Agent judgment: resolve it before delivery when
   it changes delivery scope or coordination; otherwise keep delivery usable and offer it later.
   Completion: the recommendation is timely, owner-specific, and non-blocking unless the Human
   chooses to decide it.
5. Treat a Bearing Scope choice as authority for the managed branch only. It does not accept
   undisclosed Roadmap, Gate, Effort, Binding, or native planning meaning. When the branch requires
   any of that new meaning, show one complete owner-separated candidate and obtain Human acceptance
   before any canonical or native write. Direct acceptance of a complete candidate already shown
   with the disposition is sufficient. Completion: every required planning write has exact
   acceptance without duplicate confirmation.
6. Continue the accepted Bearing Scope through its required semantic owners and exact native
   binding. Continue Standalone Native Work through normal delivery without enrollment. Completion:
   implementation follows the accepted disposition and the original request remains usable in
   either branch.

## After this operation

- **Required:** Reuse the visible disposition for a reliable direct continuation. Ask again only
  when a materially new scope or conflict appears.
- **Consider:** Keep several separable scopes and a complete visible candidate in one Human decision
  when their boundaries are clear.
- **Do not infer:** A request being new, material, complex, or repository-local establishes the
  required relationship. Missing planning objects, an unbound native inspection, apparent
  simplicity, or permission to proceed also does not place a scope in either disposition.

## Completion criterion

One minimal orientation identified every proposed native scope, ordinary scope continued without a
governance prompt, each material planning opportunity received at most one timely owner-specific
recommendation, the Human explicitly chose Bearing Scope or Standalone Native Work for each related
scope before implementation, and delivery continued without automatic enrollment.
