# Bearing Setup

Own repository integration lifecycle and orchestrate explicit Project Catalog maintenance. This internal branch continues from established public orientation and never re-enters the public router; preserve the current request and resume it after successful initialization.

## Process

1. **Inspect.** Read `$HOME/.bearing/kit/current/skills/bearing/references/shared/planning-transaction.md`, package metadata, current Catalog state, `.bearing/manifest.json` when present, supported root Agent Surface files, selected-surface Work-management Pointers, `.bearing/state/`, `.bearing/cache/`, `.bearing/executor-profiles/`, and every `.scratch/*/effort.md`. A v1 selected-surface pointer is exactly one standalone `Work-management contract: \`<repository-relative-locator>\`` declaration; ordinary mentions, examples, zero declarations, multiple declarations, and selected-surface disagreement are not pointers. Classify the Repository Integration Lifecycle from facts. Do not discover executors or infer provider compatibility from an installed skill. Completion: lifecycle, current surface, provider prerequisite, Catalog health, user-owned files, and every candidate target are inventoried.
2. **Select the branch.** Choose initialize, reconcile, incompatible repository cutover, deactivate, purge, Catalog rename, forget, relink, or confirmed reset from the request. Package uninstall belongs to the package manager. Catalog maintenance never substitutes for repository lifecycle. Completion: one branch and its preservation boundary are explicit.
3. **Resolve decisions conversationally.** Report detected facts first, then ask one material decision at a time in the current user's language. The running Agent Surface is the primary fact. Resolve selected surfaces, the one compatible Matt provider prerequisite, and only user-nominated executor candidates. Never present Generic as a choice, scan installed skills, or batch unrelated decisions. Completion: every required choice is explicit and no inspectable fact became a question.
4. **Propose the exact write set.** Initialize or reconcile establishes state and cache, writes the manifest and Provider Configuration plus any explicitly accepted project-owned profiles, and adds concise managed pointers. Reconcile removes only deselected managed blocks. Re-resolve every existing registration and produce a current structured semantic assessment; an unchanged assessment preserves the profile without replaying a user decision, while missing or materially changed source semantics require an explicit assessed update, retain, or remove disposition. Deactivate changes the manifest to `deactivated` and removes its registered managed pointers and disposable cache while preserving state, Provider Configuration, profiles, backups, and durable artifacts. Purge inventories every destructive target and preserves durable project artifacts. Catalog rename changes only one alias; forget changes only registration; relink changes one locator and never moves files. Confirmed reset replaces the exact SQLite Catalog database state with a fresh empty schema and requires explicit Setup re-registration afterward. Completion: semantic effect, preserved data, and exact repository and user-level targets are visible.
5. **Obtain acceptance.** After all decisions are known, present one final owner-separated Apply review covering external prerequisites already completed, the exact repository Apply Unit, preserved user and Matt content, and the later independent Catalog effect. Require one explicit Apply acceptance. An incompatible cutover is the exception with two distinct consents: accept the upgrade direction after read-only inventory, then confirm the complete inspected Apply. Relinking while the old repository remains available requires an earlier move-versus-copy decision. Reset requires confirmation that every registration will be discarded and re-registration will be manual. Completion: the accepted scope is unambiguous and no second Apply confirmation remains.
6. **Apply and validate.** Re-read the complete set. Use the Planning Transaction for repository lifecycle and shared Catalog primitives for user-level operational state. Fresh initialization with no nominations uses `bearing setup --repo <repo-root> --surface <surface> --provider-contract <repository-relative-locator>`; repeat `--surface` only for explicitly selected surfaces. Active and Reactivation calls pass a current `--executor` plus assessment for every unchanged or updated existing registration; missing or materially changed registrations instead pass the accepted `--retain-executor` or `--remove-executor` disposition. Active material repair adds `--confirm-repair`. Reactivation adds `--confirm-reactivate` only after retained configuration revalidation. A supported 0.1.0 cutover first uses `--plan --cutover-at <reviewed-ISO-timestamp>` to inspect the exact Recovery Bundle location, object counts, path dispositions, preserved native scopes, exclusions, and generation-bound confirmation token; after both consents, repeat the same selection and timestamp with `--accept-upgrade-direction --confirm-cutover --cutover-plan-token <reviewed-token>`. Any generation change invalidates the token and requires a new review and consent. An accepted deactivation uses `bearing deactivate --repo <repo-root>`. An accepted purge first uses `bearing purge --repo <repo-root> --plan`; the confirmed call repeats the exact token with `--confirm-purge --purge-plan-token <reviewed-token>` and exactly one of `--recovery-export <external-path>` or `--accept-no-recovery-export`. Repository validation commits before the independent Catalog operation; a Catalog failure yields a truthful pending-resumption outcome and never rolls back or relabels the valid repository Apply. Use Catalog maintenance commands only for their matching accepted branch. Never edit Catalog files directly or discover repositories by scanning. Completion: repository and Catalog outcomes are explicit and every successful target validates.
7. **Initialize project synthesis.** After successful Fresh initialization, compose the Project Summary owner with the accepted initialization context so it creates or refreshes the canonical long-horizon synthesis. Initialization does not invoke Project Brief Refresh, write `.bearing/state/project-brief.md`, or invent a Brief to fill a visual surface. Completion: Summary and absent Brief remain separate truthful states.
8. **Offer the optional Scope Review.** After successful Fresh Setup, offer one optional Bearing Scope Review through the public `governance-disposition` contract. Acquire a transient Work Management inventory only if the user accepts the offer, discard it after the review, and make no repository, provider, Portal, or canonical write. For an Active project, run the same review only when the user explicitly requests it; never repeat the Fresh offer on routine activation. Completion: the offer or explicit review outcome is visible without changing Bearing Scope.
9. **Resume.** When composed from an uninitialized request, return the branch outcome to the existing public orchestration with the original request unchanged. Completion: setup is not mistaken for completion of project work.

## Fresh Setup Journey

Report detected facts before asking anything. Ask one material decision at a time and only when it cannot be resolved from current evidence. A matching instruction file for the running Agent Surface requires no redundant question. When neither instruction file exists, ask whether to create `AGENTS.md`, `CLAUDE.md`, or both. Preserve every unselected surface byte-identical.

A missing Matt prerequisite routes to its owning capability. If the user accepts, let that owner finish, revalidate the result, and resume Setup in the same visible continuation. Refusal produces no Bearing repository writes. A compatible selection records exactly one `matt-skills/v1` Provider Configuration containing its resolved contract locator. Bearing never stores or asks for a tracker driver, rewrites the Matt contract, falls back from an unsupported contract, or inspects native scope outside an explicitly accepted transient Scope Review.

The optional executor question accepts zero or more familiar skill names or commands, and zero nominations is a complete Fresh configuration. Never scan, rank, recommend, install, whitelist-match, prefer, or select a default executor. Resolve only the exact nominated skill on the user-selected Agent Surface. Read its `SKILL.md` and directly required local execution-contract references, then make an explicit semantic assessment of whether that owned contract covers end-to-end execution and the final outcome or writeback. Do not infer eligibility from keywords or ask the deterministic CLI to interpret free prose. The structured assessment must list the exact directly required local reference locators, contain the explicit eligibility conclusion, quote exact source excerpts for execution ownership and final writeback, and provide one evidence excerpt for every proposed native artifact and writeback behavior; pass it with the matching `--executor-assessment`. Explain that planning, testing, TDD, debugging, and review helpers remain supporting skills. An unavailable, malformed, ambiguous, or insufficient nomination may be retried or skipped and never blocks Fresh completion.

Each accepted assessment creates one surface-scoped project-owned Execution Profile with a stable key, familiar display name, portable surface-qualified capability locator, source-supported native-artifact rule and writeback behavior, durable-evidence rule, fallback-receipt behavior, and executor-profile provenance. Show the familiar name and concise writeback summary for explicit confirmation before Apply. Multiple registrations coexist without cross-surface deduplication, priority, preference, or default semantics. Registration installs or changes no skill. The package-owned Generic evidence-reconciliation fallback remains hidden during Setup, creates no repository profile, grants no native Ticket lifecycle authority, and is disclosed only when an actual later writeback matches no specialized registration.

After decisions are complete, show one final owner-separated Apply review. The repository Apply Unit contains the active manifest, Provider Configuration, any explicitly accepted profiles, and managed blocks on selected surfaces. Re-read and validate the complete virtual result before writing it atomically. Catalog registration follows repository validation as an independent outcome.

An applied Fresh outcome states the selected surfaces, verified Matt contract, configured nominations or none, repository validation, and Catalog result. It explicitly states that Setup created no Roadmap, Milestone Gate, Effort, Work Binding, or Matt-owned mutation. Portal availability is optional, but the Fresh completion handoff is required: finish exactly one Portal handoff branch below before proceeding to the one optional Scope Review offer in step 8.

## Portal Handoff

After successful Fresh Setup, reactivation, cutover, or Catalog reset plus Setup re-registration, probe only the configured loopback origin: use `BEARING_PORT` when present, otherwise `http://127.0.0.1:4178`. Never scan other ports or processes, and never start Portal automatically.

Probe `<origin>/healthz`. Report an active Portal only when it identifies a compatible Bearing package and read-model and the current Catalog Entry is readable from that Host. Then provide the exact `<origin>/projects/<catalog-entry-id>` project URL. If the Host is reachable but incompatible, tell the user to stop it and start Portal from the current kit in a separate terminal. If no Host is reachable at the configured origin, tell the user to run `bearing portal` in a separate terminal and that the current project will appear in the Catalog.

The Portal handoff never changes Setup success or becomes another user decision. Fresh completion may include a foreground start hint; a routine Active no-op does not repeat that recommendation, though it may provide the verified current-project URL when a compatible Host is already available.

## Incompatible Repository Cutover

Trigger cutover only from an inspected legacy repository schema or integration contract. A package-version difference alone never authorizes migration. Before the first consent, perform a read-only inventory and explain the source and target schemas, preserved canonical history, transformed or removed Bearing-owned paths, untouched Matt-native scopes, explicit executor re-nomination rule, and the verified Recovery Bundle prerequisite. Declining the direction writes nothing.

After direction acceptance, resolve the current surface and Matt contract and assess only explicitly nominated executors. Unknown legacy shapes, duplicate identities, broken references, invalid State, or ambiguous profile disposition stop in recovery before backup creation. Generate one canonical UTC timestamp for the reviewed Apply and keep it unchanged between `--plan` and Apply.

The second consent covers the plan's exact Recovery Bundle path, object counts, path dispositions, managed-block changes, nominated registrations, preserved Matt-native scopes, exclusions, and independent Catalog effect. Only then pass both consent flags. Apply creates and verifies a durable bundle before conversion. The bundle contains all old canonical State, transformed Effort sidecars, manifest, provider/profile sources, and only the exact managed blocks—not cache, native work, unmanaged surrounding content, or external Asset payloads. It records source and target schemas, per-entry hashes, inventory, and a verified receipt.

Conversion is one protected repository transaction: move Efforts into `.bearing/state/efforts/` with one provider/driver/native-scope Work Binding, replace the lifecycle manifest and Provider Configuration, retain only freshly qualified executor registrations, replace selected managed pointers, remove legacy sidecars, discard old cache contents, rebuild Sync projections, and validate zero diagnostics. A pre-commit failure restores the old integration while retaining the verified Recovery Bundle. Catalog reconciliation remains a later independent stage; failure is `partial` with an idempotent resumption point. Never delete a Recovery Bundle automatically.

- One transient Work Management inventory only during an accepted Fresh review or explicit Active-project Scope Review; discard it before completion

## Write Set

- Initialize/reconcile: `.bearing/state/`, `.bearing/cache/`, `.bearing/manifest.json`, `.bearing/provider.json`, explicitly accepted `.bearing/executor-profiles/*.md`, and managed root pointers
- Cutover: one verified `.bearing/backups/0.1.0-to-0.1.1-<timestamp>/` Recovery Bundle followed by the exact inspected conversion targets; never Matt-native files or unmanaged Agent Surface bytes
- Post-validation Catalog stage: idempotent Catalog upsert with an independent outcome
- Deactivate: registered managed pointers, manifest status, disposable cache, then removal of the matching Catalog entry
- Purge: only the explicitly accepted Bearing-owned delete set, then removal of the matching Catalog entry
- Catalog operations: `$HOME/.bearing/catalog.sqlite` only through the Catalog domain API; reset also clears the exact default-journal state before publishing a fresh empty schema

Never stage, commit, or edit `.gitignore`. Never delete mocks, prototypes, source, native evidence, or other durable project artifacts merely because Bearing is deactivated, purged, forgotten, or relinked.
Bearing Scope Review never adds inventory, recommendations, or dispositions to any write set.

## Outcomes

- `applied`: the complete accepted operation validates.
- `no-op`: repository integration or Catalog state already matches.
- `awaiting-decision`: surfaces, profiles, destructive scope, move-versus-copy, reset consequence, or proposed writes await acceptance.
- `partial`: the validated repository Apply is complete while an independent cross-owner stage such as Catalog registration remains pending and resumable.
- `blocked`: adapter support is absent, validation or rollback prevents trustworthy repository state, or Catalog availability prevents the requested user-level mutation.
- `cancelled`: the user declines a prerequisite, configuration decision, or final Apply; no unaccepted Bearing repository write occurs.

## Recovery

Retain original bytes and remove only transaction-created repository targets when a repository transaction fails before commit. Purge commits when the exact `.bearing` namespace is atomically detached. If recursive cleanup then fails, do not rename a partially deleted quarantine back into place or claim restoration: return `blocked` with the exact typed cleanup-residue path, keep the repository outcome applied, and continue the independent Catalog removal attempt. If a committed repository lifecycle operation is followed by Catalog failure, do not roll back the repository: return `partial` with separate `Repository` and `Catalog` outcomes, then retry reconcile or lifecycle removal idempotently. An unavailable Catalog permits only confirmed empty reset followed by explicit Setup re-registration; it never restores a backup, repairs a lock, or discovers repositories. Report attempted, restored, and currently changed targets. A customized profile conflict is `awaiting-decision` before writes, never an overwrite.

## Completion Criterion

The selected repository lifecycle or Catalog state is explicit, every accepted target matches it, preserved data remains present, no repository-local Bearing contract or skill copy exists, split outcomes are reported truthfully, and any original project request has returned to its governing runbook.
